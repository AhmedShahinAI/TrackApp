# Security Strategy

Generated by `/security-assess` on 2026-10-17 for branch `001-foundation-access-roster` (HEAD `204749d`
plus uncommitted work). Read-only assessment: no application code, configuration, database or remote
was changed. Secret values were not read into this document; only variable names and paths appear.

**Overall verdict: not ready for production.** The application layer is strong and already reviewed
twice ([security-review-001.md](../security-review-001.md), [security-review-002.md](../security-review-002.md)),
with zero open defects there. This assessment found what those reviews did not cover: **one data-protection
incident in the repository (G-01)**, **one access-control hole on the API stack (G-02)**, a brute-force
gap at sign-in (G-03), and an operations layer (backups, TLS, alerting, rollback) that exists only on paper.

> **Correction (2026-10-17): G-01's "real student data" is unverified.** The owner states that no real
> student data was intentionally uploaded. The classification rests on circumstantial evidence only: the
> file's download-servlet name, its exact registrar layout, cohort-like ID patterns, an Excel author
> field that is not the owner's, and earlier project documents that call it "real" without verifying
> it. It stands as **suspected** until the owner checks the backup against a real section. If it proves
> synthetic, G-01 drops to Info, Phase 2 is withdrawn, and Phase 1's redaction remains as harmless
> hygiene. The evidence log records the full fact/assumption breakdown.

## Scope

- **In scope:** everything in the repository: `app/`, `routes/`, `config/`, `bootstrap/`,
  `database/`, `resources/`, `public/`, `tests/`, `.github/workflows/`, `docs/runbook-deploy.md`,
  the tracked contents of `design-system/`, and the untracked `design-system-v1/` folder that sits
  in the working tree.
- **Baseline:** the two prior OWASP reviews. Their fixed findings (001 F-01–F-04, 002 F-01–F-06)
  and residual risks (001 R-01–R-05, 002 R-01–R-06) are inherited, not re-litigated. Where this
  assessment depends on one, it cites it by ID.
- **Out of scope:**
  - The production host. None exists yet; the PRD targets a KSA-hosted VM, with university IT
    approval pending for 2026-11-12.
  - Initiatives, submissions, dashboards and notifications. These are PRD P0 features with no code
    yet, so their surfaces must be assessed when they land.
  - Dynamic penetration testing.
- **Regulatory frame:** Saudi PDPL and university information-security policy (PRD §4.4, §8.7). The
  worst plausible incident is disclosure of student identity data (University IDs and names).

## Trust Boundaries

1. **Internet → public support endpoints.** Anonymous, hostile by assumption. Guarded by rate
   limits, proof of work, honeypot, constant response time, generic refusals.
2. **Browser → staff web/API.** Authenticated session cookie (Secure, HttpOnly, SameSite=Lax) with
   CSRF on both stacks. The API stack trusts the session without re-checking that the account is
   still active (G-02).
3. **Role → role.** INSTRUCTOR < BRANCH_COORDINATOR < SUPER_ADMIN, enforced by `can:` middleware
   plus global scopes (`BranchScope`, `SectionScope`).
4. **Branch → branch.** Coordinators see only their branches, and instructors only their sections.
   Enforced by global scopes on Section, SectionEnrollment, Student, ImportJob, AuditLog and
   SupportRequest, with scoped route-model binding (`RouteServiceProvider.php:48-70`).
5. **Uploaded file → parser.** Untrusted xlsx/csv, roster data from the registrar.
6. **App → database.** The app's DB user must not be able to UPDATE or DELETE `audit_logs`
   (deploy gate `track:audit-grants --strict`).
7. **App → Redis.** Sessions, cache, rate-limit counters and serialized queue payloads (001 R-05).
   Must be private and password-protected.
8. **Developer workstation / repo → GitHub.** Anything committed reaches `origin`
   (`github.com/AhmedShahinAI/TrackApp`, which an unauthenticated request cannot see, so it is
   presumed private) and every clone and CI runner.
9. **CI → artifacts.** Playwright failure artifacts (screenshots of fixture data) are kept 14 days.
10. **Production host → backup store.** Encrypted dumps leave the host.

## Threat Model

Actors:
- **Anonymous internet user**, including bots.
- **Impersonator** who knows a valid University ID.
- **Instructor**, **coordinator** and **super admin**, each of whom may be malicious or compromised.
- **Recently deactivated staff member.**
- **Someone with repo access**: a collaborator, a future contractor, or anyone who gets a leaked clone.
- **Network-adjacent attacker** (shared lab machine, same Wi-Fi).
- **Host or DB operator.**

```text
Asset: student names + University IDs
Actor: anyone with read access to the repo or any clone/fork/CI checkout
Boundary: workstation -> git history -> GitHub origin
Threat: bulk personal-data disclosure; copies spread with every clone and cannot be recalled
Control: repo appears private; .env ignored
Gap: real roster spreadsheet committed in 8c723b6 and present on origin/main (G-01)
Layer: S1 ADOPT
```

```text
Asset: student roster and section data reachable through /api/v1
Actor: staff member who has just been deactivated, or a thief of a session cookie after the victim's password reset
Boundary: browser -> /api/v1 (web + auth:sanctum, without `active` / `session.auth`)
Threat: continued read and write access for the rest of the session (60 min idle, renewable indefinitely)
Control: deactivation deletes session rows, but only when SESSION_DRIVER=database; production is redis
Gap: API stack never re-checks is_active or the password hash (G-02)
Layer: S2/S3 ADOPT
```

```text
Asset: staff account (especially SUPER_ADMIN)
Actor: anonymous attacker with a list of institutional emails (they are predictable)
Boundary: internet -> POST /login, POST /api/v1/auth/login
Threat: online password guessing spread across IPs; 8-char letter+digit policy, no 2FA by owner decision
Control: 5 failures/60 s per email+ip, Argon2id, no user enumeration
Gap: no per-account limit, raw IPv6 addresses not bucketed, no alert on failure spikes (G-03, G-04, G-20)
Layer: S2/S9 ADOPT
```

```text
Asset: section access (who sees which students)
Actor: super admin making a mistake, or an attacker with a super-admin session
Boundary: PATCH /sections/{id}/instructor and POST /sections (instructor_id)
Threat: student data handed to a deactivated account, a coordinator outside the branch, or a user in another organization
Control: can:section.change_instructor (super admin only); StoreSectionRequest limits to active org users
Gap: change-instructor validates only exists:users,id (G-08); instructors can name any active user on create (G-14)
Layer: S3 ADOPT
```

```text
Asset: coordinator's or admin's workstation
Actor: instructor who controls a section_number or course text
Boundary: SectionController CSV export -> spreadsheet application
Threat: a cell beginning with = + - @ executes as a formula when the export is opened
Control: xlsx exports use StringCell
Gap: CSV export uses raw fputcsv (G-07)
Layer: S4 PARTIAL
```

```text
Asset: student roster files
Actor: anyone who later gains file-system or backup access
Boundary: storage/app/private (+ rsync backup)
Threat: every roster ever uploaded stays on disk and in every backup, forever
Control: private disk, UUID names, serve=false
Gap: no deletion after completion or cancel and no retention job (G-05)
Layer: S5 PARTIAL
```

```text
Asset: availability + recovery of all data
Actor: hardware failure, ransomware, operator error
Boundary: production host -> backup store
Threat: data loss beyond RPO 24 h; no tested way back from a bad deploy
Control: runbook §5 documents an encrypted mysqldump and a quarterly restore rehearsal
Gap: nothing schedules or monitors the backup; no rollback procedure (G-19)
Layer: S10 ADOPT
```

holder of a reference), 002 R-03 and R-06 (retention versus audit log, awaiting the DPO), 002 R-05

## Current Controls

These are verified and should be preserved. Plans must not weaken them, and most are pinned by tests.

- **Sign-in**
  - Decoy-hash timing equalisation and a single generic failure message.
  - The inactive check runs after the password check.
  - The session is regenerated on login. Logout calls invalidate and then regenerateToken.
  - Remember-me is disabled.
  - `LoginController.php`, `LoginTest.php`.
- **Hashing:** Argon2id with `rehash_on_login` (`config/hashing.php:20,51-53,68`).
- **Session cookies:** Secure, HttpOnly, SameSite=Lax, JSON serialization, 60-minute idle lifetime (`config/session.php`).
- **Authorization**
  - `can:` on every API route, enforced by `EveryRouteAuthorizedTest`.
  - Global scopes with scoped route binding: out-of-scope records return 404, not 403.
  - Last `scope.bypass_all` holder is protected; self-deactivation is refused.
  - `password`, `is_active` and roles are not mass-assignable.
- **CSRF**
  - On web, API and public stacks, with no exclusions.
  - The private disk is not served (001 F-01, `CsrfCoverageTest`).
- **CSP and headers**
  - CSP is `script-src 'self'` with no inline or eval, using the Alpine CSP build.
  - Also sets `frame-ancestors 'none'`, `object-src 'none'`, nosniff, Referrer-Policy, Permissions-Policy, and HSTS when the request is secure.
  - Pinned by `ContentSecurityPolicyTest` and `csp.spec.ts`.
- **Output and injection**
  - No raw Blade output anywhere. `HtmlString` cells escape with `e()`.
  - Raw SQL fragments are static literals only. Sort keys and locale columns are whitelisted.
- **Uploads**
  - Extension, MIME and magic-byte checks, size limit, row limit, zip-bomb ratio.
  - UUID filenames on a private disk; files parsed on a queue with streamed openspout.
- **Public channel:** as reviewed in 002. Two-axis HMAC'd limits, PoW, honeypot, minimum fill time, constant response time with a concurrency cap, 50-bit references, `no-store`, retention sweep.
- **Audit**
  - Sign-in and logout events, failures and blocks, role, branch and password changes, deactivation, `access.denied` on every 403/404, imports, exports, support events.
  - Keys matching `password|token|secret|_hash` are redacted.
  - Append-only model guard, DB revoke and deploy gate `track:audit-grants --strict`.
- **Dependencies**
  - `composer audit --locked`: 0 advisories.
  - `npm audit`, including dev dependencies: 0 vulnerabilities (2026-10-17).
- **Secrets hygiene**
  - `.env`, `.env.backup` and `.env.production` are ignored. No key or env file appears anywhere in history.
  - Sentry has PII and SQL bindings off.
- **Monitoring:** `track:monitor` alerts on error rate, failed jobs, queue backlog or outage, disk usage, and overdue retention.

## Recommended Planning Order

Highest risk first, without breaking dependencies. Each phase is independently shippable and testable.

1. **S1 — Repository PII containment (G-01, G-12 example file).** Do this first because the exposure is
   already live and grows with every clone. It has three steps:
   - **Code-safe (no approval needed):** ignore the design-system data folders and replace the fixtures with synthetic data.
   - **History purge and force-push:** an explicit approval gate.
   - **Remote checks:** visibility, collaborators and forks.
2. **S2/S3 — Session revocation on the API (G-02, G-17).** The highest-impact code fix, and small. It
   needs tests that run on a non-`database` session driver.
3. **S2/S9 — Sign-in brute-force (G-03, plus G-04 once the owner decides).** Per-account limiter,
   IPv6 bucketing, removing the unused limiter, auditing blocks.

   widen the T053 guard so regressions are caught, then the `withoutGlobalScopes` review.

   retention, audit visibility (after the owner decides), FK change.

7. **S10 — Logging and alerting (G-10, G-20).** Can run in parallel with phases 4–6.
