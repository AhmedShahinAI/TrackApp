### Conventions

- **Working directory:** every command runs from the repository root.
- **PHP:** `PHP=/c/Users/dreng/php84/php.exe` locally. The `php` on PATH is 8.3 and cannot load
  `vendor`. CI uses `php` (8.4).
- **Test runs:** `--parallel` takes one path at a time. `tests/Feature/Audit` cannot be run as a
  directory under PHP 8.4 (`ExportSafetyTest.php` fatals on a pre-existing issue), so run its files
  singly.
- **Playwright:** its `webServer` and `global-setup.ts` call `php`. Put php84 first on PATH for the
  run, e.g. `PATH="/c/Users/dreng/php84:$PATH" npx playwright test …`.

- **Evidence:** real command output only, with counts and status. No secret values. **No real
  student names or IDs, ever**, including in this log.

### Phase 1: Repository PII containment (in-tree)

**Scope:** G-01 in the working tree and every future commit. No history rewrite (that is Phase 2) and no remote action.

Files in scope:

- `design-system/scratch/roster.xlsx`
- `.gitignore`
- the affected `tests/Visual/baselines/**`
- one new architecture test

**Approach (fixed here so the implementer does not choose):**

- **Redact the spreadsheet; don't regenerate it.**
  - Build the synthetic export by rewriting **only** `xl/sharedStrings.xml` inside the real `.xlsx`.
    Every other part of the zip stays byte for byte. This keeps the registrar format quirks the
    tests exist to prove (`RegistrarRealFileTest` imports the file "unmodified"), and removes only
    the 22 IDs and 22 names.
  - Course, campus, section and status labels are not personal data, so they stay.
- **Mapping table**
  - Map each real value to one synthetic value:
    - IDs: 9-digit, matching the default University ID pattern, in a reserved block
      `999000001`–`999000022`. First check that the block doesn't collide with the seeder's
      other students.
    - Names: fictional six-part Arabic names of similar length, so the layouts stay comparable.
  - Use the same mapping in every file, so the seeder, the kit and the xlsx still agree. The
    reference-screen comparisons depend on that.
- **Where the mapping lives**
  - The mapping holds the real values, so it is **never written inside the repository**.
  - Keep it at `%USERPROFILE%\track-pii-mapping\mapping.json`, or another owner-chosen path
    outside the repo. Phase 2 reuses it as the `git filter-repo --replace-text` input.
  - Delete it when Phase 2 closes, or when D-1 is declined.
- **Scan script**
  - A scan script beside the mapping, also outside the repo, counts how many of the real values
    appear in each tracked file and in each visual baseline's OCR-free proxy (see Validation).
  - It prints counts and paths only. It is the same check as the one behind the strategy's G-01
    numbers.
- **Untracked copies**
  - Affected: `design-system/scratch/roster_sample.xlsx`,
    `design-system/uploads/filedownloadservlet(21)-4d54b7af.xlsx` and `design-system-v1/`.
  - **⛔ Confirm before moving:** move them to an owner-chosen folder outside the repo. Don't
    delete them; the owner keeps the originals.
  - `RegistrarRealFileTest.php:139` scans every `.xlsx` under `design-system/` by content. A real
    copy left there would fail its "one distinct export" pin.
- **Guard (durable)**
  - A new `tests/Architecture/NoPersonalDataFixturesTest.php` asserts four things:
    - every tracked `.xlsx`/`.csv` is in an allowlist with its SHA-1 and the note "synthetic";
    - the only University-ID-shaped tokens in the registrar fixture are in the `999000xxx` block;
    - the design-system data folders are gitignored (`git check-ignore`);
    - `design-system-v1/` is gitignored.
  - It cannot embed the real values; hashes of 9-digit IDs are trivially reversible. So it guards
    the shape, and the out-of-repo scan proves the content.
- **Baselines**
  - Regenerate only the baselines whose screens render seeded student, section, import or audit
    data. Candidates by name: `*-students`, `*-student-detail`, `*-section-*`, `*-sections-*`,
    `*-imports`, `*-step-importing`, `*-audit-*`, `*-instructor-no-sections`.
  - Diff each one to confirm the only change is text in table and detail cells.
  - Windows: local `--update-snapshots` on the specs that own them.
  - Linux: a CI run with `--update-snapshots`, committed from there.
- **Rebuild local databases:** local SQLite databases built from the old seeder still hold real
  names. That means `%TEMP%\track-local.sqlite` and `%TEMP%\track-visual.sqlite`. Rebuild them
  after the seeder change.

**Tasks:** see Phase 1 in `SECURITY-TASKS.md` (SEC-010 to SEC-025).

**Validation:**

### Phase 4: Sign-in brute force

**Scope:** G-03, plus G-04 once D-2 and D-3 are decided.

Files:
- `app/Modules/Authentication/Http/Controllers/LoginController.php:68,97,243-246`
- `app/Providers/AppServiceProvider.php:70-76`
- `app/Modules/Support/Services/SupportLimits.php` (reuse `addressBucket`)
- `PasswordPolicy.php`, `ResetPassword.php` and the first-login flow, for D-3

**Approach:**
- Keep the existing `email+ip` limiter: 5 per 60 s.
- Add an **account-level** limiter keyed on the lowercased email alone: **20 failures per 15 minutes,
  then 15 minutes blocked**. It is a proposed default and goes in the settings table if the
  `support_throttle_*` pattern fits.
- Bucket the IP part with `SupportLimits::addressBucket` (IPv6 /64).
- The block response stays identical to the current one: same message, same status, same timing
  floor. **No enumeration regression.**
- Emit `auth.login_blocked` with a reason of `account` or `address`.
- Delete the unused `login` named limiter, or route through it. Pick one; don't leave both.
- **Accepted trade-off to record:** an attacker can lock a known account out for 15 minutes. Staff
  can still be helped by a super admin clearing the limiter. If there's no command for that, add
  `track:login-unblock {email}`.
- G-04, after D-2: change `PasswordPolicy::MIN_LENGTH`; existing users are unaffected until their
  next change.
- G-04, after D-3: an admin reset sets a `password_change_required` flag. A middleware on the web
  and API stacks then redirects or returns 403 until the user changes the password. The policy
  change applies to that new password.

**Evidence:** test names and totals; proof that the response for an account-level block is
